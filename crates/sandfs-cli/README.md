# sandfs-cli

The `sandfs` command: mount a [sandfs](https://crates.io/crates/sandfs-core) workspace as a real directory, so any program can read and write it. The source underneath, such as a host folder, is never modified; every write lands in a copy-on-write overlay. Forking never copies the source, and `changes` lists the files a workspace added, modified or deleted.

It mounts on Linux with FUSE 3 (`fusermount3`, package `fuse3`). A mount answers only the user who mounted it, and root too when `/etc/fuse.conf` has a `user_allow_other` line (or root made the mount), which a container started by a root daemon such as Docker needs in order to use the folder. On macOS sandfs serves the workspace over NFS on localhost and mounts it with macOS's own NFS client, so nothing needs installing or approving; it answers only the user who mounted it and root. Install it with `cargo install sandfs-cli`. Every command is also a method of the [`sandfs`](https://crates.io/crates/sandfs) library, for a program that wants workspaces without running this one. On Windows you get everything but mounting: `serve --mcp`, `changes`, `list` and `rm`, with `sandfs serve --mcp SOURCE` creating a workspace over a source.

```bash
sandfs mount ~/datasets/survey ~/ws/survey       # a host folder, never written to
sandfs mount ~/finance ~/ws/finance --read-only contracts   # contracts/ can be read but not changed
sandfs fork ~/ws/survey ~/ws/cleanup             # survey's changes so far, without copying the folder
python clean.py ~/ws/cleanup                     # real files, any tool
sandfs shell cleanup -- python clean.py          # the same, seeing no other files of the machine
sandfs changes ~/ws/cleanup                      # A/M/D against the source
sandfs changes cleanup --since survey            # A/M/D against another workspace of the same source
sandfs changes cleanup report --copy-to ~/keep   # write the changes under report/ into ~/keep
sandfs unmount ~/ws/cleanup                      # changes stay saved
sandfs mount cleanup ~/ws/cleanup                # and come back
sandfs fork cleanup --name cleanup-1             # a snapshot, kept but not mounted
sandfs fork ~/code/app ~/ws/task --branch task   # a copy of a clone, uncommitted work included
sandfs fork ~/notes ~/ws/notes                   # any folder as it is now, its files cloned (APFS, btrfs, XFS)
sandfs list                                      # workspaces and where they are mounted
sandfs update cleanup ~/datasets/survey-v2       # move a workspace onto a newer source
sandfs rm cleanup                                # forget a workspace and its changes
sandfs rm --unmount ~/ws/survey                  # unmount it first if it is mounted
sandfs clean                                     # free the space downloaded repository files take
```

`--read-only PATH` (repeatable, relative to the source) makes a file or folder read-only in a new workspace and its forks: programs can read it, but writing, deleting, renaming or creating there fails as on a read-only file system (`EROFS`), and its files show without write permission. It is how a container or an agent given the mount gets to look at a folder without changing it even in its own copy. `serve --mcp SOURCE --read-only PATH` does the same for an agent over MCP. It is set when a workspace is created; mounting an existing workspace with it is refused.

`sandfs fork FROM DIR` takes, as FROM, a workspace's name, the folder it is mounted on or any folder in it, or a folder of a git repository on this machine that sandfs doesn't mount. For a repository it makes a workspace over `HEAD` and writes into it what the repository's folder has changed since: modified, staged, new and deleted files, links and the executable bit, as `git status` sees them, but not ignored files. It is a copy taken once, so later edits in the folder don't reach the workspace, and `changes` lists those files from the start. In the copy, what was staged shows as not yet staged. The repository is only read; files are read whole into memory as they are copied, so a very large uncommitted file costs that much memory once. Any other folder is copied as it is now, so later edits there don't reach the fork either: its files, links and folders are cloned, with their modes and times, into `$SANDFS_HOME/copies`, which takes no space for their contents and about a second per 10,000 files, and the copy goes when the last workspace over it is removed. That needs the folder and `$SANDFS_HOME` on one disk that clones files (APFS, btrfs, XFS); elsewhere, as on ext4 or with the folder on another disk, the fork is refused rather than copied in full, naming the folder and the home. `--allow-copy` copies such files in full instead, which takes as much space as the folder and the time to copy it (`update` then copies the same way), and `mount` gives a live view of the folder instead. Pipes, sockets and devices are left out. `--branch NAME` starts git in the fork on a new branch NAME at the commit FROM is on, keeping its files and what it has staged, as `git switch -c` would; the fork's `origin` is the repository (or the remote one, for a remote repository's workspace), so `git push origin NAME` brings its commits back, and a branch name the repository or FROM already has is refused. `--read-only PATH` adds read-only paths to those FROM has.

`sandfs update NAME [SOURCE]` moves a workspace onto a newer version of its source and keeps its own changes. A mounted one moves in place: its changes are saved first, and the mount then reads as the newer source, while a shell in one of its folders and files left open carry on (an open file the newer source removed still reads as it was). SOURCE is another folder, or another commit of the same repository; without it the source is looked up again as it was given, so a `git:` source or URL moves to the newest commit of its branch (a fixed `@revision` stays put, and a host folder has nothing newer). A file the newer source changed and the workspace didn't now reads as it is there. A change of the workspace's that matches the newer source stops counting as one, which is how files a `git pull` in the mount brought in leave its changes. A path changed in both is printed as `C path` and keeps the workspace's version; for a commit, the older version is still in git (`git show OLDCOMMIT:path`, with the commit `update` names on stderr). Nothing is copied: saved files stay where they are, and the workspace's forks stay on the source they had. Base files the newer commit changed report the time of the update as their modification time, so build tools see them as changed and rebuild only those. In a git workspace, git's index is built again for the new commit, so files staged with `git add` show as not staged (a new file as untracked), and `HEAD` and branches at the old commit, or at one the new commit comes after, follow it; a branch or `HEAD` at a commit made in the workspace is refused, since moving would leave that commit behind, so push it first. A file that a `git pull` in the workspace brought in counts as upstream's, not the workspace's, even when upstream changed it again since. A host folder is compared file by file with the newer one, only where the workspace changed something.

`sandfs shell NAME [-- COMMAND...]` runs your shell, or a command, in a mounted workspace with the rest of the machine's files out of its reach: it starts in the mount and can change what isn't read-only there, run the system's programs and use a temporary folder of its own, but can't read your home folder, other folders or the workspace's source. It gets no network unless `--network` is given, HOME is an empty folder outside the mount (so caches don't land among the changes), and only PATH, TERM, the locale, USER and SHELL pass through from your environment, so tokens and keys in it stay out; with `--network` the proxy variables do too. Git works in a git workspace (it reads the local copy's objects, nothing else of it), though without sandfs's file monitor, so `git status` reads the files it is asked about. Anything the command leaves running ends with it, except on macOS a process that moves itself into a session of its own; and descriptors sandfs was itself started with stay open in the command, so don't hand it any you mean to keep from it (#137). Its exit code is the command's. This is how an agent that works through a shell gets the mount as its only files. Sandfs still enforces nothing itself: on Linux the command runs under bubblewrap (package `bubblewrap`), on macOS under the system's own sandbox (`sandbox-exec`), with a profile sandfs writes for the mount. Ubuntu 23.10 and later restrict the user namespaces bubblewrap needs, so there it may need an AppArmor profile that allows them (or `sysctl kernel.apparmor_restrict_unprivileged_userns=0`).

`sandfs shell` gives a program the whole network or none of it. To let one reach some sites and not others, run it under Anthropic's [sandbox runtime](https://github.com/anthropic-experimental/sandbox-runtime) (`srt`) instead, with the mount as the only folder it may write to. `srt` confines a program with the same tools (bubblewrap on Linux, the system's sandbox on macOS) and sends its network through a proxy that lets through only the sites listed. It lets a program read the whole machine unless told otherwise, so hide your home folder, and the workspace's source if it lives elsewhere, then allow the mount back:

```json
{
  "network": { "allowedDomains": ["pypi.org", "files.pythonhosted.org"], "deniedDomains": [] },
  "filesystem": {
    "denyRead": ["~", "/srv/survey"],
    "allowRead": ["~/ws/survey"],
    "allowWrite": ["~/ws/survey"],
    "denyWrite": []
  }
}
```

```bash
sandfs mount /srv/survey ~/ws/survey --read-only raw
cd ~/ws/survey && srt --settings ~/survey-srt.json -c 'my-agent'
sandfs changes survey
```

Read-only paths stay read-only under `srt`, and `changes` lists what the program wrote as usual. Unlike `sandfs shell`, `srt` keeps HOME and the rest of your environment, so take tokens out of it yourself. Writes under a hidden home folder are refused on macOS and, on Linux, go to an empty folder that is thrown away when the command ends. Git in a `git:` workspace doesn't work this way: it reads objects from the repository the workspace came from (or sandfs's local copy of it under `$SANDFS_HOME`), which the settings above hide. Use `sandfs shell` for git workspaces, or add that repository's `.git/objects` to `allowRead` and allow writes to the mount; git then warns that its file monitor can't reach sandfs and reads the files itself instead.

`sandfs changes NAME [PATH...] --copy-to DIR` is how changes leave a workspace: it writes the files listed (all of them, or those under each PATH) into DIR, copying added and modified files and links with their executable bit and removing deleted ones, so a copy of the source kept in DIR comes to match the workspace. It writes nothing outside DIR and never writes through a link it finds there. DIR may be the source folder itself, which is how a host folder keeps an agent's work: name it on purpose, since that is the one time sandfs changes the source. It also leaves out changes in a `.git` folder, in any spelling a Mac or Windows disk would read as one, since git runs the programs named there; it says how many it left out, and you copy those by hand if you mean to. It never loses work done in DIR meanwhile: a file there that differs both from what the workspace started from and from what the copy would make it, as one edited in DIR since, refuses the whole copy before anything is written, and the error names each such file; `--force` copies anyway. A file DIR lacks is always written, so an empty DIR takes the changes as before. The check compares with the workspace's start: its source, plus the uncommitted files a fork of a clone copied in (or the `--since` workspace). For a workspace mounted straight over a host folder (`sandfs mount FOLDER DIR`) and copied back into it, the source is the folder as it is now, so there it can't tell an edit made since; `sandfs fork FOLDER DIR` keeps the folder as it was, so the check works.

`sandfs serve --mcp NAME` hands an unmounted workspace to an agent as MCP file tools over stdin and stdout (read, list, glob, grep, write, edit, move, delete, changes), with the source's files under `/mnt`. Each change is saved before its reply, so a later `mount` or `changes` sees it, and a change that can't be saved is undone and reported as an error.

One process serves a workspace at a time. A mount or an MCP session holds it until it ends, a second one is refused with the holder's name, and a crashed holder releases it. Parallel attempts each get their own fork.

Every mount runs in one background process, which the first mount starts and which exits a moment after the last `unmount`. It writes its log to `$SANDFS_HOME/run/server.log`. Mounts of one git commit, such as a workspace and its forks, share its git readers and every folder listing read from it.

Changes are saved under `$SANDFS_HOME` (default `~/.local/share/sandfs`) once a file has gone a quarter of a second without a write. Closing a file doesn't save it, since the mount is never told about opens and closes. These saves are written to disk but not flushed, so they survive the mount's process crashing but not necessarily a power cut. `fsync` saves at once and flushes to disk before it returns, and `unmount`, `fork` and `changes` save and flush everything first. On macOS `fsync` doesn't: the Mac sends each write to the mount before the write returns, so a fork or `changes` sees it, and with that setting it never passes `fsync` on. There a write is flushed to disk only by `unmount`, `fork` or `changes`, which matters to programs that count on `fsync`, such as databases. A file being written goes straight into a file on disk under `$SANDFS_HOME`, not into memory, and once saved it is read from there through the kernel's page cache, so a mount's memory doesn't grow with what programs write in it and a file can be as large as the disk allows. Writing into part of a saved file first copies it, which takes no time on filesystems that clone files (APFS, btrfs, XFS) and is a full copy on others (ext4); a file from the source is copied on its first write. A fork on disk costs more than a fork in memory. `sandfs fork` never copies the source, but it waits for the workspace's latest changes to be saved, links each changed file into the fork (copying it where the disk can't link), and starts a new mount, which reads a host folder again rather than sharing what the first mount has read (mounts of one git commit do share it). Without a directory, `sandfs fork NAME --name SNAPSHOT` stops before the mount: it keeps a snapshot of the workspace as it is now, which `fork SNAPSHOT DIR` brings back as a new copy (or `mount SNAPSHOT DIR` mounts and changes the snapshot itself). With the files already saved it costs a link per changed file: 45 ms for a workspace holding a 1.1 GB build. A host folder is read as it is when each path is first touched, so mount one nothing else is changing. `git:<path or url>[@rev]` mounts a commit instead of a folder (a URL works without `git:`); for a remote repository sandfs fetches only that commit and its folder listings, with no history, and fetches file contents when they are first read. Contents fetched from a remote repository are kept in one local copy per repository, shared by its workspaces, until `sandfs clean`: for each repository none of whose workspaces is mounted or served, it drops the file contents and keeps the commits and folder listings, so the workspaces still mount at once and fetch a file again when it is next read, and it deletes the copy of a repository no workspace uses any more. Offline, a commit id that was mounted before still mounts and the folders opened before still read; a branch or tag name is looked up on the server every time, so it doesn't mount offline.

A git mount shows a `.git` folder, which makes it a checkout of the mounted commit: on the branch it was mounted as (the remote's default branch when no revision is given), or at the commit for a commit id or tag. Git works in it as in any checkout, and what it writes (the index, commits, branches) goes into the workspace like any other change, so forks carry it; `changes` leaves `.git` out, so it lists only the files themselves. Objects are read from sandfs's local copy of the repository, which is never written to; the folder's `origin` is the repository the mount came from, so `git push` goes there, and git fetches file contents it needs as the local copy does. From a remote repository, the history before the mounted commit isn't there (`git fetch --deepen` brings more); a local repository's history is all there, read from the repository itself. Git's index lists every file without reading it: git's file monitor (`core.fsmonitor`) runs `sandfs git-fsmonitor`, which answers with the files the workspace has changed, so `git status` reads only those. Symbolic links are part of the checkout like files; submodules, which a mount doesn't show, are left out of it (`skip-worktree`) rather than reported deleted. `git commit` in a partial clone checks that it has every file's contents, so `.git` also lists the files the local copy lacks, as loose objects in `.git/sandfs-objects`, without fetching them. A commit then fetches only the files git compares, the others in each folder on the way to a change, into the local copy: one file, then from a folder's second the whole folder at once. Git's settings in `.git` can name programs for git to run, and anything that can write to the mount can change them, so don't run git yourself in a mount that a program you don't trust can write to. `changes` lists `.git` apart from the files: it names any change to `.git/config` or `.git/hooks` on stderr, so a review sees one; `serve --mcp` refuses changes to a git mount's `.git` for that reason (a host folder holding its own `.git` gets no such protection).
