# sandfs-cli

The `sandfs` command: mount a [sandfs](https://crates.io/crates/sandfs-core) workspace as a real directory, so any program can read and write it. The source underneath, such as a host folder, is never modified; every write lands in a copy-on-write overlay. Forking never copies the source, and `changes` lists the files a workspace added, modified or deleted.

It mounts on Linux with FUSE 3 (`fusermount3`, package `fuse3`). A mount answers only the user who mounted it, and root too when `/etc/fuse.conf` has a `user_allow_other` line (or root made the mount), which a container started by a root daemon such as Docker needs in order to use the folder. On macOS sandfs serves the workspace over NFS on localhost and mounts it with macOS's own NFS client, so nothing needs installing or approving; it answers only the user who mounted it and root. Install it with `cargo install sandfs-cli`. On Windows you get everything but mounting: `serve --mcp`, `changes`, `list` and `rm`, with `sandfs serve --mcp SOURCE` creating a workspace over a source.

```bash
sandfs mount ~/datasets/survey ~/ws/survey       # a host folder, never written to
sandfs mount ~/finance ~/ws/finance --read-only contracts   # contracts/ can be read but not changed
sandfs fork ~/ws/survey ~/ws/cleanup             # survey's changes so far, without copying the folder
python clean.py ~/ws/cleanup                     # real files, any tool
sandfs changes ~/ws/cleanup                      # A/M/D against the source
sandfs changes cleanup --since survey            # A/M/D against another workspace of the same source
sandfs changes cleanup report --copy-to ~/keep   # write the changes under report/ into ~/keep
sandfs unmount ~/ws/cleanup                      # changes stay saved
sandfs mount cleanup ~/ws/cleanup                # and come back
sandfs fork cleanup --name cleanup-1             # a snapshot, kept but not mounted
sandfs list                                      # workspaces and where they are mounted
sandfs rm cleanup                                # forget a workspace and its changes
sandfs clean                                     # free the space downloaded repository files take
```

`--read-only PATH` (repeatable, relative to the source) makes a file or folder read-only in a new workspace and its forks: programs can read it, but writing, deleting, renaming or creating there fails as on a read-only file system (`EROFS`), and its files show without write permission. It is how a container or an agent given the mount gets to look at a folder without changing it even in its own copy. `serve --mcp SOURCE --read-only PATH` does the same for an agent over MCP. It is set when a workspace is created; mounting an existing workspace with it is refused.

`sandfs changes NAME [PATH...] --copy-to DIR` is how changes leave a workspace: it writes the files listed (all of them, or those under each PATH) into DIR, copying added and modified files and links with their executable bit and removing deleted ones, so a copy of the source kept in DIR comes to match the workspace. It writes nothing outside DIR and never writes through a link it finds there. DIR may be the source folder itself, which is how a host folder keeps an agent's work: name it on purpose, since that is the one time sandfs changes the source. It also leaves out changes in a `.git` folder, in any spelling a Mac or Windows disk would read as one, since git runs the programs named there; it says how many it left out, and you copy those by hand if you mean to.

`sandfs serve --mcp NAME` hands an unmounted workspace to an agent as MCP file tools over stdin and stdout (read, list, glob, grep, write, edit, move, delete, changes), with the source's files under `/mnt`. Each change is saved before its reply, so a later `mount` or `changes` sees it, and a change that can't be saved is undone and reported as an error.

One process serves a workspace at a time. A mount or an MCP session holds it until it ends, a second one is refused with the holder's name, and a crashed holder releases it. Parallel attempts each get their own fork.

Every mount runs in one background process, which the first mount starts and which exits a moment after the last `unmount`. It writes its log to `$SANDFS_HOME/run/server.log`. Mounts of one git commit, such as a workspace and its forks, share its git readers and every folder listing read from it.

Changes are saved under `$SANDFS_HOME` (default `~/.local/share/sandfs`) once a file has gone a quarter of a second without a write. Closing a file doesn't save it, since the mount is never told about opens and closes. These saves are written to disk but not flushed, so they survive the mount's process crashing but not necessarily a power cut. `fsync` saves at once and flushes to disk before it returns, and `unmount`, `fork` and `changes` save and flush everything first. On macOS `fsync` doesn't: the Mac sends each write to the mount before the write returns, so a fork or `changes` sees it, and with that setting it never passes `fsync` on. There a write is flushed to disk only by `unmount`, `fork` or `changes`, which matters to programs that count on `fsync`, such as databases. A file being written goes straight into a file on disk under `$SANDFS_HOME`, not into memory, and once saved it is read from there through the kernel's page cache, so a mount's memory doesn't grow with what programs write in it and a file can be as large as the disk allows. Writing into part of a saved file first copies it, which takes no time on filesystems that clone files (APFS, btrfs, XFS) and is a full copy on others (ext4); a file from the source is copied on its first write. A fork on disk costs more than a fork in memory. `sandfs fork` never copies the source, but it waits for the workspace's latest changes to be saved, links each changed file into the fork (copying it where the disk can't link), and starts a new mount, which reads a host folder again rather than sharing what the first mount has read (mounts of one git commit do share it). Without a directory, `sandfs fork NAME --name SNAPSHOT` stops before the mount: it keeps a snapshot of the workspace as it is now, which `fork SNAPSHOT DIR` brings back as a new copy (or `mount SNAPSHOT DIR` mounts and changes the snapshot itself). With the files already saved it costs a link per changed file: 45 ms for a workspace holding a 1.1 GB build. A host folder is read as it is when each path is first touched, so mount one nothing else is changing. `git:<path or url>[@rev]` mounts a commit instead of a folder (a URL works without `git:`); for a remote repository sandfs fetches only that commit and its folder listings, with no history, and fetches file contents when they are first read. Contents fetched from a remote repository are kept in one local copy per repository, shared by its workspaces, until `sandfs clean`: for each repository none of whose workspaces is mounted or served, it drops the file contents and keeps the commits and folder listings, so the workspaces still mount at once and fetch a file again when it is next read, and it deletes the copy of a repository no workspace uses any more. Offline, a commit id that was mounted before still mounts and the folders opened before still read; a branch or tag name is looked up on the server every time, so it doesn't mount offline.

A git mount shows a `.git` folder, which makes it a checkout of the mounted commit: on the branch it was mounted as (the remote's default branch when no revision is given), or at the commit for a commit id or tag. Git works in it as in any checkout, and what it writes (the index, commits, branches) goes into the workspace like any other change, so forks carry it; `changes` leaves `.git` out, so it lists only the files themselves. Objects are read from sandfs's local copy of the repository, which is never written to; the folder's `origin` is the repository the mount came from, so `git push` goes there, and git fetches file contents it needs as the local copy does. From a remote repository, the history before the mounted commit isn't there (`git fetch --deepen` brings more); a local repository's history is all there, read from the repository itself. Git's index lists every file without reading it: git's file monitor (`core.fsmonitor`) runs `sandfs git-fsmonitor`, which answers with the files the workspace has changed, so `git status` reads only those. Symbolic links are part of the checkout like files; submodules, which a mount doesn't show, are left out of it (`skip-worktree`) rather than reported deleted. `git commit` in a partial clone checks that it has every file's contents, so `.git` also lists the files the local copy lacks, as loose objects in `.git/sandfs-objects`, without fetching them. A commit then fetches only the files git compares, the others in each folder on the way to a change, into the local copy: one file, then from a folder's second the whole folder at once. Git's settings in `.git` can name programs for git to run, and anything that can write to the mount can change them, so don't run git yourself in a mount that a program you don't trust can write to. `changes` lists `.git` apart from the files: it names any change to `.git/config` or `.git/hooks` on stderr, so a review sees one; `serve --mcp` refuses changes to a git mount's `.git` for that reason (a host folder holding its own `.git` gets no such protection).
