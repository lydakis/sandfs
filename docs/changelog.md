# Changelog

## 0.4.1

- **Symbolic links**: a workspace can hold symbolic links (`Kind::Symlink`; `Workspace::symlink` and `read_link`, `symlink(path, target)` and `read_link(path)` in Python). A link is stored as its target and never followed by the workspace: `read`, `write` and `set_executable` refuse one instead. `changes()` reports links like files. A host folder's links are now listed as links instead of skipped, and still never lead a read outside the folder; each keeps the meaning it has on the host wherever the workspace is mounted, except that a link into the folder reaches the workspace's copy. Mounted folders support `ln -s` and `readlink` on Linux and macOS, so `python3 -m venv` and npm's `.bin` links work in a mount, and saved workspaces keep their links. A source may list links too: its `read` of one returns the target. Matching on `Kind` needs the new variant.
- **Mounting on macOS**: `sandfs mount` works on macOS with nothing to install. The mount's process serves the workspace over NFS on localhost and macOS's own NFS client mounts it, with no kernel extension, macFUSE or sudo. Writes are saved by the same rule as on Linux, except that `fsync` doesn't reach the server and saves nothing by itself. Like a FUSE mount, it answers only the user who mounted it (and root).
- **README**: rewritten for newcomers. It explains what sandfs is for in plain terms, starts with one short example, then covers each kind of source (with a git example), giving a workspace to an agent, mounting it as a folder, performance tables (parallel attempts, and mounting VS Code and Chromium from GitHub against cloning them) and the limits.
- **sandfs-cli speed**: the FUSE mount tells the kernel it needn't open or close files, so a first read of a small file is about a quarter faster and rereads and overwrites take about 40% less time.
- **sandfs-cli saving**: closing a file no longer commits it. A write is saved once its file has gone 250 ms without a write, on `fsync`, or at `unmount`, `fork` or `changes`. A program that writes a file, closes it and exits still has it saved a moment later, but not at the instant of the close.
- **sandfs-cli ranged reads**: large host-folder files read in ranges go back to the folder only for the parts the kernel hasn't kept in its page cache.
- **Benchmarks**: `sandfs-bench --remote URL` mounts a large repository from a git server and compares it with full, shallow, blobless and sparse clones: time until the files are readable, scattered reads, a folder search, a second copy, peak memory and disk.
- **Readahead for folders**: a source can take a hint that a folder's files are about to be read (`Source::prefetch`, `prefetch(path, recursive)` in Python) and fetch them in one trip. The workspace gives it for a folder once two of its files are needed (`ls -l` asking for sizes a listing left out, or a walk such as `grep -r` reading), and for everything below a folder once a walk has read files in three folders in it without pausing; a single read, a lookup and a walk that only lists (`find`) never do. The git source uses it to fetch up to 1,000 files in one request and no longer fetches anything just to list a folder, and the mount leaves unknown sizes out of its listings. On a VS Code mount from GitHub, `find` over a 992-file folder went from 67 s to 0.8 s and `grep -r` from 63 s to 3.3 s.
- **Benchmarks**: `sandfs-bench --only everyday` times everyday operations (ls, ls -l, find, stat, cat, grep -r, create, edit, mv, rm, changes) on a host folder, a slow source and a remote repository, through the Rust API and through the mount.
- **sandfs-cli memory**: a mount no longer keeps a copy of every file it has read, since the kernel's page cache already holds them. A host folder's files are read in the ranges the kernel asks for, and a git mount keeps only the last few files it read, so the kernel's chunks of one file read it once. Eight mounted forks doing the README's workflow peak at 104 MiB instead of 781 MiB, and eight git mounts searching an 83 MiB folder hold 95 MiB instead of 772 MiB. Reading small files through a host-folder mount is 10 to 15% faster.
- **sandfs-core speed**: on Linux, listing a host-folder directory checks that it is still inside the folder with one call instead of resolving every folder on the way, so reaching a file 65 folders down on a fresh workspace takes 0.8 ms instead of 3.5 ms. On Linux, a listing through a folder swapped for a symlink since it was listed is now refused even when the link points inside the folder, as reads already were.
- **sandfs-cli, one process for every mount**: mounts no longer get a process each. The first `mount` or `fork` starts a background process that serves every mount, and it exits a moment after the last `unmount`. Its log is `$SANDFS_HOME/run/server.log`, replacing each workspace's `mount.log`. Mounts of one git commit, such as a workspace and its forks, share its git readers and every folder listing read from it. Eight mounted forks doing the README's workflow peak at 70 MiB instead of 104 MiB and are made in 28 ms instead of 50; eight git mounts of a 10,000-file commit searching it at once hold 206 MiB instead of 465 MiB, at the same speed. If that process crashes, every mount goes with it, not just one.
- **sandfs-cli, git inside git mounts**: a `git:` mount has a `.git` folder, so git works in it: `status`, `add`, `commit`, branches and `push`. It starts on the branch the commit was mounted as (the remote's default without a revision), borrows the objects of sandfs's local copy without writing to it, and keeps what git writes in the workspace, so forks carry commits and branches (`sandfs changes` leaves `.git` out). `git status` reads no files: git's file monitor asks `sandfs git-fsmonitor`, which reports the files the workspace changed, so status on a VS Code mount takes 0.07 s after its first run. From a remote repository the history before the mounted commit isn't there (a local repository's is), and a `commit` fetches only the files git compares, the others in each folder on the way to a change: on VS Code, a first commit changing two files takes 2.3 s and fetches 0.5 MiB. Workspaces record the branch in `workspace.json`; ones saved before still load, starting at the commit. `serve --mcp` refuses to change files in `.git`, whose config names commands git runs.
- **sandfs-git listing speed**: listing folders of a fresh remote git mount no longer starts a git process per folder to learn which files are still on the server. The first listing starts one walk of the whole commit in the background, and later listings use its answer. On a VS Code mount from GitHub, the first `find` takes 1.1 s instead of 9.2 s, and the first `git status` 3.4 s instead of 12 s.
- **sandfs-git missing files**: `GitSource::missing_files` lists the files of the commit a partial clone lacked, by blob id (`ObjectIds`), found by the same walk listings use.
- **Readahead for programs reading by path**: a build or test run opens the files it needs without listing folders, and those reads now count toward readahead when they come one after another, as a walk's do; reads with pauses between them, as a person's, still don't. A long walk asks for each part of a tree as it reaches it (the folder holding its last three folders), and a folder is asked for even when a parent was. On a fresh VS Code mount from GitHub, reading every file of a 992-file folder by path took 2.0 s instead of 101 s.
- **Benchmarks**: the `--remote` comparison also runs a developer's day in each copy: the first `git status`, a commit of one changed file, `git status` again and `grep -r` over the whole copy.
- **sandfs-cli, saved files stay on disk**: a mount holds a file in memory only until it is saved. From then on it reads the file from its saved copy on disk, so the kernel's page cache decides what stays in memory, and a mount (or a fork of it) loads saved files without reading them. After a debug build of sandfs-cli inside a mount the background process holds 185 MiB instead of 794 MiB, and forking that workspace takes 1.4 s instead of 5.9 s and leaves it at 87 MiB instead of 1.6 GiB. Moving, copying or making executable a saved file no longer writes it again.
- **sandfs-cli durability**: the README says exactly when a mount's writes reach the disk, and that on macOS `fsync` returns without flushing them. Having the Mac pass `fsync` on would mean having it hold writes back until a file is closed and then save the workspace at every close, which made writing many small files over three times slower (#96 tracks a cheaper way).
- **sandfs-cli large files**: a mount writes files straight to disk instead of memory, and the 4 GiB limit on a mounted file is gone. A 4 KiB write in the middle of a 3 GiB file peaks at 13 MiB of memory instead of 6 GiB. Once the file is saved, the same write takes 4 ms instead of 5 s on a filesystem that clones files (XFS here, APFS on a Mac); on ext4 it still copies the file once. A debug build of sandfs-cli inside a mount leaves the background process at 10 MiB instead of 187 MiB.
- **sandfs-cli flushing many files**: a fork, `changes` or `fsync` that must flush more than 64 saved files to disk does it with one call for the whole disk on Linux (`syncfs`), instead of one per file. Forking a mount right after `npm install` wrote 6,200 files takes 0.35 s instead of 0.8 s (3.4 s before files were written straight to disk).
- **sandfs-core changes**: `Workspace::changes` reports a written file of `COMPARE_LIMIT` (64 MiB) or more as modified without reading it and the file it replaced to check whether the bytes are the same. Before, every save of a mount read such a file whole, twice.
- **sandfs-cli snapshots**: `sandfs fork NAME --name SNAPSHOT`, without a directory, keeps a fork without mounting it, to bring back later with `fork SNAPSHOT DIR`. It costs a save and a link per changed file: 45 ms for a workspace holding a 1.1 GB build.
- **sandfs-core stored files**: a file's bytes can stay in a source of the caller's instead of memory. `Workspace::write_stored` writes such a file, `Workspace::store` moves a file's bytes there once they are saved, keeping its version, and `Workspace::stored` says where a file's bytes are. A stored file is read from its source every time and never cached.
- **sandfs-git large trees**: a walk through a tree missing more than 1,000 files, such as `grep -r` over a whole mounted repository, used to fetch them a folder at a time; the git source now fetches them in the background, 1,000 at a time in the order the walk reads them, for as long as files keep being read (a search that stops early stops the fetch too). On a fresh VS Code mount from GitHub, `grep -r` over all 20,891 files took 8.6 s instead of 9 minutes, and reading a 992-file folder by path 0.12 s instead of 2.0 s. Fetches no longer run git's automatic maintenance (`maintenance.auto`, `gc.auto`) in sandfs's copy of the repository, which ran after every fetch and repacked it as fetches piled up.
- **sandfs-git parallel reads**: a `GitSource` read by several threads at once starts more `cat-file` readers, up to one per CPU, instead of making every read wait for one.
- **sandfs-cli copies**: the FUSE mount handles `copy_file_range`, so copying a file inside a mount (`cp`, or a build tool keeping a cache) shares the bytes, including a saved file's copy on disk, instead of passing them through the kernel twice. Building this repository's `sandfs` command with cargo inside a mount of a host folder: a rebuild after changing one file takes 1.9 s instead of 2.6 s (1.1 s in a plain folder), and the first build 26 s instead of 29 s (26-27 s). Most of the rebuild gap left comes from hard links, which the mount still refuses, so cargo copies its cache files instead. `sandfs-bench --only build` measures it.
- **sandfs-cli missing names**: the FUSE mount lets the kernel remember that a name isn't there, as it already remembered names that are, so a program probing for files asks once instead of every time. Loading Express's test suite with mocha probes about 3,700 missing names; a warm load took 0.61–0.75 s instead of 0.83–0.91 s (0.58–0.76 s in a plain folder). Creating, moving or copying a file in the mount shows it at once; a file added to a host folder behind the mount's back, which was never guaranteed to show, can now take up to a minute to appear under a name looked up before.

## 0.4.0 (2026-10-19)

A rewrite. sandfs is now a general-purpose sandbox filesystem with a Rust core, and the Python package is a thin binding over it. Nothing from the 0.2 API carries over.

- **Workspaces**: mount read-only sources at paths, keep every write, directory and deletion in a copy-on-write overlay, and fork in O(1). Forks share everything already read but never see each other's changes.
- **Sources**: a host directory (`DirSource`), in-memory files (`MemorySource`), a git commit read without a checkout (`GitSource`, faster in a partial clone), or any Python object with `list(path)` and `read(path)`.
- **Changes**: `changes()` lists every added, modified or deleted file. The harness decides what to keep and writes it back.
- **Bytes first**: files are bytes of any kind. `stat` always reports an exact size and a version, and `write(..., expected_version=...)` rejects a write to a file that changed since it was read.
- **Large files**: `read(path, offset=..., length=...)` reads one range without caching the whole file. A source can define `read_range` to serve ranges itself.
- **Concurrency**: calls release the GIL, and forks reading the same uncached file fetch it from the source once.
- **sandfs-mcp**: an MCP server exposing a copy-on-write workspace as nine file tools (read, list, glob, grep, write, edit, move, delete, changes); `sandfs-mcp --dir MOUNT=PATH`. A path holding a control character or line separator is shown as a quoted JSON string, so one name can't read as two lines.
- **sandfs-cli**: the `sandfs` command mounts a workspace as a real directory over FUSE on Linux; `sandfs mount`, `fork`, `changes`, `unmount`. Sources are a host folder or `git:<path or url>[@rev]`; a remote repository mounts in about a second, since only the mounted commit and its folder listings are fetched, with no history. File contents are fetched when first read. A branch or tag name is looked up on the server at every mount; a commit id mounted before also mounts offline. Changes are saved on disk between mounts. `sandfs serve --mcp NAME` serves a workspace to an agent as MCP file tools instead.
- **sandfs-cli speed**: the FUSE mount keeps the kernel's cache for files that haven't changed, lists directories with their attributes, skips flushes on files opened read-only and polls for mounts in milliseconds, so rereading small files takes half the time, stat after a listing is 25× faster and `sandfs fork` returns in 7 ms instead of 54.
- **sandfs-core speed**: workspaces resolve a path in one lookup instead of one per directory and host-folder reads check the file they opened instead of resolving each parent folder first, so a stat 64 folders deep is about 12× faster and creates and deletes about a third faster.
- **sandfs-cli concurrency**: one process serves a workspace at a time. A second mount or `serve --mcp` of a workspace in use is refused instead of saving over the first, as is a second mount on the same directory. `unmount` fails if the final save failed, `serve --mcp` undoes and reports a change it couldn't save, and `changes` reads a workspace safely while another process is saving it. Building `sandfs-cli` now needs Rust 1.89 (the library crates still build with 1.85).
- **Benchmarks**: `sandfs-bench`, an unpublished crate, times sandfs through the Rust API and the FUSE mount against the host filesystem and overlayfs, including a workflow of parallel attempts that search, edit and check their files (`--only workflow`); `cargo run --release -p sandfs-bench -- --scratch /dev/shm`.
- **sandfs-cli on macOS and Windows**: the `sandfs` command builds there with everything but the mount, and `sandfs serve --mcp SOURCE` creates a workspace over a source. The library crates and the Python package are tested on macOS and Windows in CI.
- **Packaging**: one abi3 wheel per platform covers Python 3.11 and later. The Rust crates `sandfs-core`, `sandfs-git`, `sandfs-mcp` and `sandfs-cli` are published alongside.
- **Removed**: the bash-like shell, host-command bridge, Python executor, access policies, storage adapters, write hooks, symlinks, text edit and unified diffs.
