# Changelog

## Unreleased

- **sandfs-cli, task copies**: `sandfs fork` makes the copy to hand one task, wherever it starts. FROM can now be a folder of a git repository on this machine, such as a clone: the fork is its `HEAD` plus what its folder has changed since (changed, staged, new and deleted files, links and modes, but not ignored files), copied once, so the copy keeps its starting point while work goes on in the folder, and `changes` lists them from the start; what was staged shows as unstaged in the copy, and the repository is only read. FROM can also be any folder inside a mount. `--branch NAME` starts git in the fork on a new branch at FROM's commit, keeping its files and index, so its commits go back with `git push origin NAME`; a name the repository or FROM already has is refused. `--read-only PATH` adds read-only paths. `sandfs rm --unmount NAME` (or the mount's directory) unmounts a workspace and deletes it in one step. README gains a git-to-sandfs table.
- **sandfs-cli, git settings in a mount never run as you**: sandfs asked a server for its branches (`mount git:URL`, `fork --branch`) by running git in the folder it was started in, so started inside a mount, it took that mount's `.git/config`, which any program writing to the mount can set to run a command (a remote rewritten to an `ext::` program, say). It now asks from an empty folder, and `fork --branch` asks a partial clone's remote by its URL, not through the repository's settings. `mount git:PATH` refuses a repository inside a mounted workspace, pointing to `sandfs fork` instead.
- **sandfs-cli, `changes --copy-to` keeps work done where it copies**: a file in DIR that differs from both what the workspace started from and what the copy would write, such as one edited there since, now refuses the copy before anything is written, naming each such file; `--force` overwrites as before. A deleted file below a link, or replaced by a folder, in DIR is left alone instead of failing the copy.
- **sandfs-cli, many mounts at once**: commands run inside a mount, and every git command there (git asks `sandfs git-fsmonitor`), found their workspace by reading the system's mount table once per workspace, so they slowed down as mounts were added. With 10,000 copies of one repository mounted, `git status` in one of them took 86 s and `sandfs list` 95 s; they now take 0.06 s and 0.13 s, as with one mount.
- **sandfs-cli, more mounts per process**: the one process that serves a home's mounts stopped at a few hundred mounts on a system that limits a process to 1,024 open files (most Linux systems; macOS allows 256), and on Linux it crashed at about 3,100, taking every mount down with it, once its threads used up the memory maps a process may have (`vm.max_map_count`). It now raises its open-file limit as far as the system allows, saves every mount's changes from 4 shared threads instead of one per mount, tells the kernel about stale folder listings from one shared thread, and refuses a new mount it has no room for with an error naming the limit. On Linux each mount now takes 2 threads instead of 4, so one process serves about 7,000 mounts with the default limit (more with `sysctl -w vm.max_map_count=262144`).
- **sandfs-cli, a fork of a plain folder**: `sandfs fork FOLDER DIR` now takes any folder, not only a workspace or a git repository: the fork is the folder as it is now, its files cloned with their modes and times into `$SANDFS_HOME/copies` (no space for their contents; 20,000 files in 1.8 s on btrfs), so later edits in the folder stay out and `changes --copy-to FOLDER` can tell an edit made there since. The copy is deleted with the last workspace over it, or by `sandfs clean`. It needs the folder and `$SANDFS_HOME` on one disk that clones files (APFS, btrfs, XFS) and is refused elsewhere, such as on ext4, rather than copied in full. `--branch` is refused for a plain folder.

## 0.5.1 (2026-10-22)

The same code as 0.5.0, released again so that it reaches PyPI. The 0.5.0 crates and GitHub release (with the `sandfs` downloads) came out, but the PyPI upload failed because the release workflow handed PyPI the `sandfs` archives along with the Python packages. It now uploads only the Python packages.

## 0.5.0 (2026-10-21)

The main changes:
- `sandfs mount` works on macOS with nothing to install.
- A repository mounts from a plain URL, and listing it, `stat` and `git status` download almost nothing.
- Git works inside a git mount.
- Workspaces and mounts hold symbolic and hard links.
- Read-only paths, `sandfs shell` and `changes --copy-to` let a workspace be all the files an agent has.
- Forks, saves and memory cost far less after a large build.
- Each GitHub release now carries the `sandfs` command, ready to run, for Linux and macOS.

Breaking changes for Rust code that matches on these types or builds their entries:
- `Kind` has a new variant, `Kind::Symlink`, so a `match` over it needs an arm for links.
- `Error` has a new variant, `Error::ReadOnly`, so a `match` over it needs one too.
- `SourceEntry` has a new field, `modified`, so a source that builds entries field by field must set it (`None` is fine).

Every change:

- **Prebuilt `sandfs` command**: each GitHub release has `sandfs` built for Linux (x86_64 and aarch64, linked statically against musl so it runs on any distribution) and macOS (Apple silicon, Intel), so the command needs no Rust toolchain. Download the archive for your machine from the release page, unpack it and put `sandfs` on your `PATH`. `sandfs-cli`'s license is now `MIT AND BSD-3-Clause`, since it carries nfsserve's NFS server.
- **sandfs-cli, writes kept under memory pressure**: on Linux, a file written and closed could lose what was written if the kernel, short of memory, forgot it within a quarter second of the last write. Git's index was the usual victim (`index file smaller than expected`). Such writes are now kept.
- **sandfs-cli, quicker unmount**: unmounting no longer waits out the quarter second the mount gives a burst of writes to settle before saving it; the final save at unmount does that work. Unmounting a copy after `git status` in it went from 270 ms to 5 ms.
- **sandfs-cli, folders listed again**: on Linux the kernel now keeps each folder's listing once read and lists it again without asking the mount, until something changes that folder through the mount. A walk over folders already seen (`find`, an editor's file tree, git looking for new files) no longer costs four requests per folder. On a VS Code mount from GitHub, `find` over the whole tree takes 0.04 s instead of 0.66 s once it has run, as fast as on a clone; in the benchmark, a second walk of 10,000 files takes 5.6 ms instead of 32 ms and listing a 10,000-file folder again 1.5 ms instead of 6.7 ms.
- **sandfs-cli, listings and inode numbers agree**: once the kernel forgot a file it had seen in a kept folder listing, that listing went on giving the file's old inode number while `stat` gave a new one, so `ls -i` and tools that match the two disagreed. The mount now has the kernel drop such listings.
- **Benchmarks**: `small/walk-warm` lists every folder of the small-file tree a second time.
- **Benchmarks, tracked**: `sandfs-bench --compare BEFORE AFTER` compares two saved runs. It lists each number that moved beyond a threshold and both runs' spread, and how far each is from what it has to beat in its own run (the host folder, overlayfs, a clone). `--skip NAME` leaves workloads out. CI now runs the quick suite on main and on each pull request that changes the Rust code, on the same machine, and puts the comparison in the run's summary. Pushes to main keep their results as artifacts.
- **Benchmarks on macOS**: `sandfs-bench` runs on a Mac, with the NFS mount as its `sandfs NFS` column; overlayfs is skipped there. Memory comes from `getrusage`, `ps` and `vmmap` instead of `/proc`.
- **Benchmarks, a day of work**: the `--remote` table also times the first `git status` in the second copy, `find` over the whole copy, a second `grep -r`, and removing the second copy.
- **Read-only paths**: `Workspace::set_read_only(path, true)` makes a path and everything below it read-only in a workspace and its later forks, so whoever it is handed to can read but not change it, even in their own copy. Writes, deletes, moves and new entries there fail with the new `Error::ReadOnly`, and so does removing or moving a folder that holds the path; `is_read_only` and `read_only_paths` report them. Python: `set_read_only(path)`, `is_read_only(path)` and `mount(..., read_only=True)`, raising `OSError` with errno `EROFS`. `sandfs-mcp --read-only PATH` does the same over MCP and names the paths in its instructions to the agent. Matching on `Error` needs the new variant.
- **sandfs-cli, confined shells**: `sandfs shell NAME [-- COMMAND...]` runs a shell or a command in a mounted workspace that can't reach the machine's other files: not your home folder, other folders or the workspace's source. It has no network unless `--network` is given, HOME is an empty folder outside the mount, and only a few harmless environment variables pass through. Bubblewrap does the confining on Linux, and the system's own sandbox on macOS, so an agent working through a shell gets the mount as its only files.
- **sandfs-cli, read-only paths**: `sandfs mount SOURCE DIR --read-only PATH` and `sandfs serve --mcp SOURCE --read-only PATH` make a file or folder of the source read-only in a new workspace, and its forks keep it. In a mount, changes there fail with `EROFS` (`NFS3ERR_ROFS` on macOS) and its files show without write permission. The paths are kept in `workspace.json`; workspaces saved before have none.
- **sandfs-cli, git settings in reviews**: `sandfs changes` on a `git:` mount still leaves `.git` out of its listing, but names any change to `.git/config` or `.git/hooks` on stderr. Git runs the programs those name, so whoever reviews an agent's work sees such a change before running git in the mount.
- **sandfs-cli, keeping changes**: `sandfs changes NAME [PATH...] --copy-to DIR` writes a workspace's changes into a folder: added and modified files and links are copied with their executable bit, deleted ones removed, and only where DIR points. PATH arguments limit `changes`, with or without `--copy-to`, to some files or folders. It never writes through a link it finds in DIR, so links an agent made can't carry a later file out of it, and leaves out changes in a `.git` folder (also `.GIT` or `git~1`, which a Mac or Windows disk reads as one), since git runs the programs named there. This replaces the loop over `changes` output that broke on unusual names (#41).
- **Changes since a checkpoint**: `Workspace::changes_since(base)` lists the files that differ from another workspace, reported like `changes()`: what an attempt did after a fork kept as a checkpoint, or how two attempts forked from one checkpoint differ. It skips everything the two still share, so the cost follows what changed after they split. Python: `changes(since=other)`. MCP: `Server::changes_since(checkpoint)` makes the `changes` tool compare against a checkpoint. CLI: `sandfs changes NAME --since OTHER` for two workspaces of the same source.
- **Hard links**: a file can have several names (`Workspace::hard_link`, `hard_links` and `has_hard_links`; `hard_link(src, dst)` and `hard_links(path)` in Python). A write through any name is seen through all of them, removing one leaves the others, and a move keeps the link while a copy or a fork gets its own file. `changes()` reports each name on its own. The Linux mount supports `link(2)` with one inode per file, and saved workspaces keep links, so rustc's incremental cache and cargo, which link their files, no longer copy them through the mount. The macOS mount supports them too (NFS `LINK`), which makes small cargo rebuilds there about three times faster.
- **Symbolic links**: a workspace can hold symbolic links (`Kind::Symlink`; `Workspace::symlink` and `read_link`, `symlink(path, target)` and `read_link(path)` in Python). A link is stored as its target and never followed by the workspace: `read`, `write` and `set_executable` refuse one instead. `changes()` reports links like files. A host folder's links are now listed as links instead of skipped, and still never lead a read outside the folder; each keeps the meaning it has on the host wherever the workspace is mounted, except that a link into the folder reaches the workspace's copy. Mounted folders support `ln -s` and `readlink` on Linux and macOS, so `python3 -m venv` and npm's `.bin` links work in a mount, and saved workspaces keep their links. A source may list links too: its `read` of one returns the target. Matching on `Kind` needs the new variant.
- **Mounting on macOS**: `sandfs mount` works on macOS with nothing to install. The mount's process serves the workspace over NFS on localhost and macOS's own NFS client mounts it, with no kernel extension, macFUSE or sudo. Writes are saved by the same rule as on Linux, except that `fsync` doesn't reach the server and saves nothing by itself. It answers only the user who mounted it and root.
- **sandfs-cli, root and containers on Linux**: a Linux mount lets root in as well as the user who made it, whenever `/etc/fuse.conf` has `user_allow_other` (or root made the mount). Before, a mount made by a user refused root, so Docker couldn't bind the folder into a container.
- **README**: rewritten for newcomers. It explains what sandfs is for in plain terms, starts with one short example, then covers each kind of source (with a git example), giving a workspace to an agent, mounting it as a folder, performance tables (parallel attempts, and mounting VS Code and Chromium from GitHub against cloning them) and the limits.
- **sandfs-cli speed**: the FUSE mount tells the kernel it needn't open or close files, so a first read of a small file is about a quarter faster and rereads and overwrites take about 40% less time.
- **sandfs-cli saving**: closing a file no longer commits it. A write is saved once its file has gone 250 ms without a write, on `fsync`, or at `unmount`, `fork` or `changes`. A program that writes a file, closes it and exits still has it saved a moment later, but not at the instant of the close.
- **sandfs-cli ranged reads**: large host-folder files read in ranges go back to the folder only for the parts the kernel hasn't kept in its page cache.
- **Benchmarks**: `sandfs-bench --remote URL` mounts a large repository from a git server and compares it with full, shallow, blobless and sparse clones: time until the files are readable, scattered reads, a folder search, a second copy, peak memory and disk.
- **Readahead for folders**: a source can take a hint that a folder's files are about to be read (`Source::prefetch`, `prefetch(path, recursive)` in Python) and fetch them in one trip. The workspace gives it for a folder once two of its files are needed (`ls -l` asking for sizes a listing left out, or a walk such as `grep -r` reading), and for everything below a folder once a walk has read files in three folders in it without pausing; a single read, a lookup and a walk that only lists (`find`) never do. The git source uses it to fetch up to 1,000 files in one request and no longer fetches anything just to list a folder, and the mount leaves unknown sizes out of its listings. On a VS Code mount from GitHub, `find` over a 992-file folder went from 67 s to 0.8 s and `grep -r` from 63 s to 3.3 s.
- **Benchmarks**: `sandfs-bench --only everyday` times everyday operations (ls, ls -l, find, stat, cat, grep -r, create, edit, mv, rm, changes) on a host folder, a slow source and a remote repository, through the Rust API and through the mount.
- **sandfs-cli memory**: a mount no longer keeps a copy of every file it has read, since the kernel's page cache already holds them. A host folder's files are read in the ranges the kernel asks for, and a git mount keeps only the last few files it read, so the kernel's chunks of one file read it once. Eight mounted forks doing the README's workflow peak at 104 MiB instead of 781 MiB, and eight git mounts searching an 83 MiB folder hold 95 MiB instead of 772 MiB. Reading small files through a host-folder mount is 10 to 15% faster.
- **sandfs-core speed**: on Linux, listing a host-folder directory checks that it is still inside the folder with one call instead of resolving every folder on the way, so reaching a file 65 folders down on a fresh workspace takes 0.8 ms instead of 3.5 ms. On Linux, a listing through a folder swapped for a symlink since it was listed is now refused even when the link points inside the folder, as reads already were.
- **sandfs-cli, one process for every mount**: mounts no longer get a process each. The first `mount` or `fork` starts a background process that serves every mount, and it exits a moment after the last `unmount`. Its log is `$SANDFS_HOME/run/server.log`, replacing each workspace's `mount.log`. Mounts of one git commit, such as a workspace and its forks, share its git readers and every folder listing read from it. Eight mounted forks doing the README's workflow peak at 70 MiB instead of 104 MiB and are made in 28 ms instead of 50; eight git mounts of a 10,000-file commit searching it at once hold 206 MiB instead of 465 MiB, at the same speed. If that process crashes, every mount goes with it, not just one.
- **sandfs-cli, git inside git mounts**: a `git:` mount has a `.git` folder, so git works in it: `status`, `add`, `commit`, branches and `push`. It starts on the branch the commit was mounted as (the remote's default without a revision), borrows the objects of sandfs's local copy without writing to it, and keeps what git writes in the workspace, so forks carry commits and branches (`sandfs changes` leaves `.git` out). `git status` reads no files: git's file monitor asks `sandfs git-fsmonitor`, which reports the files the workspace changed, so status on a VS Code mount takes 0.07 s after its first run. From a remote repository the history before the mounted commit isn't there (a local repository's is), and a `commit` fetches only the files git compares, the others in each folder on the way to a change: on VS Code, a first commit changing two files takes 2.3 s and fetches 0.5 MiB. Workspaces record the branch in `workspace.json`; ones saved before still load, starting at the commit. `serve --mcp` refuses to change files in `.git`, whose config names commands git runs.
- **sandfs-git listing speed**: listing folders of a fresh remote git mount no longer starts a git process per folder to learn which files are still on the server. The first listing starts one walk of the whole commit in the background, and later listings use its answer. On a VS Code mount from GitHub, the first `find` takes 1.1 s instead of 9.2 s, and the first `git status` 3.4 s instead of 12 s.
- **sandfs-git symbolic links**: `GitSource` lists a commit's symbolic links as links (reading one returns its target) instead of skipping them, so a git mount shows them, and git in the mount treats them as part of the checkout: changing a link's target shows in `git status` and can be committed.
- **sandfs-git missing files**: `GitSource::missing_files` lists the files of the commit a partial clone lacked, by blob id (`ObjectIds`), found by the same walk listings use.
- **Readahead for programs reading by path**: a build or test run opens the files it needs without listing folders, and those reads now count toward readahead when they come one after another, as a walk's do; reads with pauses between them, as a person's, still don't. A long walk asks for each part of a tree as it reaches it (the folder holding its last three folders), and a folder is asked for even when a parent was. On a fresh VS Code mount from GitHub, reading every file of a 992-file folder by path took 2.0 s instead of 101 s.
- **Benchmarks**: the `--remote` comparison also runs a developer's day in each copy: the first `git status`, a commit of one changed file, `git status` again and `grep -r` over the whole copy.
- **sandfs-cli, saved files stay on disk**: a mount holds a file in memory only until it is saved. From then on it reads the file from its saved copy on disk, so the kernel's page cache decides what stays in memory, and a mount (or a fork of it) loads saved files without reading them. After a debug build of sandfs-cli inside a mount the background process holds 185 MiB instead of 794 MiB, and forking that workspace takes 1.4 s instead of 5.9 s and leaves it at 87 MiB instead of 1.6 GiB. Moving, copying or making executable a saved file no longer writes it again.
- **sandfs-cli durability**: the README says exactly when a mount's writes reach the disk, and that on macOS `fsync` returns without flushing them. Having the Mac pass `fsync` on would mean having it hold writes back until a file is closed and then save the workspace at every close, which made writing many small files over three times slower (#96 tracks a cheaper way).
- **sandfs-cli large files**: a mount writes files straight to disk instead of memory, and the 4 GiB limit on a mounted file is gone. A 4 KiB write in the middle of a 3 GiB file peaks at 13 MiB of memory instead of 6 GiB. Once the file is saved, the same write takes 4 ms instead of 5 s on a filesystem that clones files (XFS here, APFS on a Mac); on ext4 it still copies the file once. A debug build of sandfs-cli inside a mount leaves the background process at 10 MiB instead of 187 MiB.
- **sandfs-cli flushing many files**: a fork, `changes` or `fsync` that must flush more than 64 saved files to disk does it with one call for the whole disk on Linux (`syncfs`), instead of one per file. Forking a mount right after `npm install` wrote 6,200 files takes 0.35 s instead of 0.8 s (3.4 s before files were written straight to disk).
- **sandfs-cli forks after many writes**: a save writes small files (64 KiB or less) into one pack per save instead of one file each, so a fork links a handful of files instead of one per saved file. After `npm install` wrote 6,200 files into a mount, three forks take 0.5 s in all instead of 1.1 s, and a snapshot 0.1 s instead of 0.22 s; after a debug build of sandfs-cli the workspace holds 354 files instead of 1,459, and forking it takes 65 ms instead of 112 ms.
- **sandfs-cli forks of large workspaces**: an `fsync`, `fork` or `changes` on a mount with nothing new since its last save, and no replaced file left to delete, only flushes that save to disk instead of saving everything again, and loading a saved workspace, which every fork and remount does, looks each restored file up once or twice instead of five times. Looking up a written file no longer checks every folder above it. After writing 62,000 small files into a mount (an `npm install` ten times the usual size), a snapshot takes about 0.15 s instead of 0.7 s, and a mounted fork about 0.5 s instead of 1.4 s.
- **sandfs-core changes**: `Workspace::changes` reports a written file of `COMPARE_LIMIT` (64 MiB) or more as modified without reading it and the file it replaced to check whether the bytes are the same. Before, every save of a mount read such a file whole, twice.
- **sandfs-cli snapshots**: `sandfs fork NAME --name SNAPSHOT`, without a directory, keeps a fork without mounting it, to bring back later with `fork SNAPSHOT DIR`. It costs a save and a link per changed file: 45 ms for a workspace holding a 1.1 GB build.
- **sandfs-core stored files**: a file's bytes can stay in a source of the caller's instead of memory. `Workspace::write_stored` writes such a file, `Workspace::store` moves a file's bytes there once they are saved, keeping its version, and `Workspace::stored` says where a file's bytes are. A stored file is read from its source every time and never cached.
- **sandfs-git large trees**: a walk through a tree missing more than 1,000 files, such as `grep -r` over a whole mounted repository, used to fetch them a folder at a time; the git source now fetches them in the background, 1,000 at a time in the order the walk reads them, for as long as files keep being read (a search that stops early stops the fetch too). On a fresh VS Code mount from GitHub, `grep -r` over all 20,891 files took 8.6 s instead of 9 minutes, and reading a 992-file folder by path 0.12 s instead of 2.0 s. Fetches no longer run git's automatic maintenance (`maintenance.auto`, `gc.auto`) in sandfs's copy of the repository, which ran after every fetch and repacked it as fetches piled up.
- **sandfs-git parallel reads**: a `GitSource` read by several threads at once starts more `cat-file` readers, up to one per CPU, instead of making every read wait for one.
- **sandfs-cli copies**: the FUSE mount handles `copy_file_range`, so copying a file inside a mount (`cp`, or a build tool keeping a cache) shares the bytes, including a saved file's copy on disk, instead of passing them through the kernel twice. Building this repository's `sandfs` command with cargo inside a mount of a host folder: a rebuild after changing one file takes 1.9 s instead of 2.6 s (1.1 s in a plain folder), and the first build 26 s instead of 29 s (26-27 s). Most of the rebuild gap left comes from hard links, which the mount still refuses, so cargo copies its cache files instead. `sandfs-bench --only build` measures it.
- **sandfs-cli missing names**: the FUSE mount lets the kernel remember that a name isn't there, as it already remembered names that are, so a program probing for files asks once instead of every time. Loading Express's test suite with mocha probes about 3,700 missing names; a warm load took 0.61–0.75 s instead of 0.83–0.91 s (0.58–0.76 s in a plain folder). Creating, moving or copying a file in the mount shows it at once; a file added to a host folder behind the mount's back, which was never guaranteed to show, can now take up to a minute to appear under a name looked up before.
- **Benchmarks**: `sandfs-bench --only build --build-dir DIR --build-command COMMAND` times any command, such as a test suite, in a copy of a folder on the host and in a mount of another copy, the first time and again after `--build-change FILE` is changed. Kubernetes' `go vet` and `go test` of its image-pulling packages take 12.3 s in a plain folder and 13.3 s in a mount. `--build-parallel N` runs it in N copies, or N forks of one mount, at once: three at once take 17.2 s in plain folders and 18.2 s in forks.
- **sandfs-cli file times**: a file nobody wrote keeps its source's modification time in a workspace and a mount, also after a move, a link or a change of its executable bit (`SourceEntry::modified`, which the host-folder source fills, `Metadata::modified`, and `Workspace::modified` to get that time without reading the file) instead of the time the workspace was made, so every fork no longer looks entirely changed to tools that compare times. Go's test cache now finds its results in a fresh fork: in a fork of a Kubernetes mount, `go test` of two packages whose results are cached takes 2.7 s instead of 5.6 s (2.0 s in a copied folder), and three attempts at once 5.6 s instead of 9.5 s (3.8 s).
- **sandfs-cli restarts**: deleting `SANDFS_HOME` and mounting again at the same path no longer fails with "the mount process did not start" when the previous background process was still finishing. On its way out that process removed the new process's socket, which shared the path, so later mounts and forks could not reach the new process.
- **sandfs-cli background process**: the process serving every mount now detaches fully from the command that starts it: a session of its own, adopted by init, launchd or the nearest subreaper. A job runner that ends a job by killing its process group or tree no longer takes other jobs' mounts down with it, and a caller's `GIT_DIR` or similar no longer leaks into later mounts. Starting it costs one more short-lived process, about 2 ms on the first mount.
- **sandfs-cli output into a pipe**: `sandfs changes` and `sandfs list` piped into a reader that stops early, such as `head`, no longer panic with "failed printing to stdout"; they stop quietly.
- **sandfs-cli URLs**: a source that is a URL, such as `https://github.com/owner/repo`, mounts that repository without the `git:` prefix, which is still needed for a local repository path.
- **sandfs-cli clean**: `sandfs clean` frees the disk space a remote repository's downloaded files take. For each repository whose workspaces are all unmounted, it keeps only the commits and folder listings they need (VS Code: 88 MiB down to 1.5 MiB) and they fetch a file again when it is next read; a repository no workspace uses is deleted. Workspaces and their changes are untouched.
- **sandfs-cli after an upgrade**: on Linux, a git mount made by a mount process whose binary was replaced since it started, as by `cargo install`, names the new binary as git's file monitor instead of the deleted one, so `git status` doesn't fall back to reading every file.
- **sandfs-cli speed on macOS**: the Mac mount's NFS server spent most of its time, under load, rechecking every call of the last minute on each new call. sandfs now carries its own copy of the server (from the nfsserve crate, BSD-3-Clause, in `crates/sandfs-cli/src/nfsserve`) that does that once a second, until a release of nfsserve has the fix (huggingface/nfsserve#57). A cold debug build of ripgrep in a mount went from 65 s to 16 s, against 8 s on a clone, and a release build takes 18 s against 13 s.
- **sandfs-cli `._` files on macOS**: the `._name` files macOS writes next to files to hold their extended attributes no longer show in the mount's listings, so git doesn't commit them and cargo doesn't rebuild forks over them. macOS still reads them by name, and `rm -r` removes folders that hold them. Files with such names that are part of the data still show.
- **sandfs-cli listings on macOS**: a folder listing in the Mac mount leaves out the attributes of files whose size isn't known yet, instead of downloading them to find it, and the Mac asks for them when it needs them. On VS Code, a fresh mount downloads 4 MB instead of 24 MB, and the first `git status` takes 6.4 s instead of 16.6 s.
- **sandfs-git known sizes**: `GitSource::with_known_sizes` takes blob sizes from elsewhere, and listings report them for files whose blobs aren't local, so nothing is fetched to learn a size.
- **sandfs-cli sizes from GitHub**: a mount from github.com asks GitHub's API for every file's size while it fetches the commit (one request; a token from `GH_TOKEN`, `GITHUB_TOKEN` or the GitHub CLI raises the limit of 60 an hour), and keeps them with the local copy. `ls -l`, `find`, `du` and `stat` then download no file, in the mounted `.git` too. On a VS Code mount on macOS, `find src` (12,873 files) took 1.2 s and `du -sh src` 0.2 s, downloading nothing, and the first `git status` 5.5 s and 20 MB instead of 6.4 s and 28 MB. Other hosts, or a request that fails, work as before.
- **Readahead skips files already fetched**: a source can say which files it has at hand (`Source::is_local`, default `false`), and reading those never leads to a prefetch. The git source says so for blobs its partial clone has, including the `.gitignore` and `.gitattributes` files fetched to build the mounted index (`GitSource::fetched_elsewhere`). `git status` reads every one of those, which looked like a walk and started fetching the whole repository in the background. On a fresh VS Code mount from GitHub (Linux), the first `git status` took 1.9 s and downloaded 0.1 MB, instead of 4.7 s and 13 MB.
- **macOS mount, folder listings**: a folder listed in pages no longer loops forever when it holds two names of one hard-linked file. Each page resumed after the last entry's file id, which both names share, so the listing went back to the first name; `find` in a cargo `target` folder never finished and kept growing. Linked names now get their own place in the listing, and the plain listing (`READDIR`) resumes where it was asked to instead of from the start.
- **macOS mount, file requests**: requests no longer wait while a save goes over every changed file to leave out macOS's own files (`._name`, `.DS_Store`); that pass now runs on the save's copy. Each request also takes one trip over the loopback instead of two: the check that only the mount's owner gets in now runs inside the NFS server instead of in a relay in front of it. Messages over 2 MiB close the connection, as the relay's limit did.
- **Mounts, saves**: each save after the first starts from the one before it and looks again only at files changed since, instead of going over every changed file, so once a build has written thousands of files a save costs what the next edit changed. macOS's own files are now left out as the save goes, instead of being removed from a copy first.
- **Mounts, reads of saved files**: a file already saved to disk is read after letting go of the lock every request takes, so reading a large build output no longer holds up the requests waiting behind it.
- **sandfs-cli on macOS, Finder**: the Mac mount is made with `nobrowse`, so Finder doesn't show it as a disk in its sidebar or on the Desktop, or offer to eject it. The folder works as before.

## 0.4.0 (2026-10-19)

A rewrite. sandfs is now a general-purpose sandbox filesystem with a Rust core, and the Python package is a thin binding over it. Nothing from the 0.2 API carries over.

- **Workspaces**: mount read-only sources at paths, keep every write, directory and deletion in a copy-on-write overlay, and fork in O(1). Forks share everything already read but never see each other's changes.
- **Sources**: a host directory (`DirSource`), in-memory files (`MemorySource`), a git commit read without a checkout (`GitSource`, faster in a partial clone), or any Python object with `list(path)` and `read(path)`.
- **Changes**: `changes()` lists every added, modified or deleted file. The harness decides what to keep and writes it back.
- **Bytes first**: files are bytes of any kind. `stat` always reports an exact size and a version, and `write(..., expected_version=...)` rejects a write to a file that changed since it was read.
- **Large files**: `read(path, offset=..., length=...)` reads one range without caching the whole file. A source can define `read_range` to serve ranges itself.
- **Concurrency**: calls release the GIL, and forks reading the same uncached file fetch it from the source once.
- **sandfs-mcp**: an MCP server exposing a copy-on-write workspace as nine file tools (read, list, glob, grep, write, edit, move, delete, changes); `sandfs-mcp --dir MOUNT=PATH`. A path holding a control character or line separator is shown as a quoted JSON string, so one name can't read as two lines.
- **sandfs-cli**: the `sandfs` command mounts a workspace as a real directory over FUSE on Linux; `sandfs mount`, `fork`, `changes`, `unmount`. Sources are a host folder or `git:<path or url>[@rev]`; a remote repository mounts in about a second, since only the mounted commit and its folder listings are fetched, with no history. File contents are fetched when first read. A branch or tag name is looked up on the server at every mount; a commit id mounted before also mounts offline. Changes are saved on disk between mounts. `sandfs serve --mcp NAME` serves a workspace to an agent as MCP file tools instead.
- **sandfs-cli speed**: the FUSE mount keeps the kernel's cache for files that haven't changed, lists directories with their attributes, skips flushes on files opened read-only and polls for mounts in milliseconds, so rereading small files takes half the time, stat after a listing is 25× faster and `sandfs fork` returns in 7 ms instead of 54.
- **sandfs-core speed**: workspaces resolve a path in one lookup instead of one per directory and host-folder reads check the file they opened instead of resolving each parent folder first, so a stat 64 folders deep is about 12× faster and creates and deletes about a third faster.
- **sandfs-cli concurrency**: one process serves a workspace at a time. A second mount or `serve --mcp` of a workspace in use is refused instead of saving over the first, as is a second mount on the same directory. `unmount` fails if the final save failed, `serve --mcp` undoes and reports a change it couldn't save, and `changes` reads a workspace safely while another process is saving it. Building `sandfs-cli` now needs Rust 1.89 (the library crates still build with 1.85).
- **Benchmarks**: `sandfs-bench`, an unpublished crate, times sandfs through the Rust API and the FUSE mount against the host filesystem and overlayfs, including a workflow of parallel attempts that search, edit and check their files (`--only workflow`); `cargo run --release -p sandfs-bench -- --scratch /dev/shm`.
- **sandfs-cli on macOS and Windows**: the `sandfs` command builds there with everything but the mount, and `sandfs serve --mcp SOURCE` creates a workspace over a source. The library crates and the Python package are tested on macOS and Windows in CI.
- **Packaging**: one abi3 wheel per platform covers Python 3.11 and later. The Rust crates `sandfs-core`, `sandfs-git`, `sandfs-mcp` and `sandfs-cli` are published alongside.
- **Removed**: the bash-like shell, host-command bridge, Python executor, access policies, storage adapters, write hooks, symlinks, text edit and unified diffs.
